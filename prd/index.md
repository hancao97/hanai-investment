# Hanai Investment 产品需求文档

> 版本：v0.1  
> 状态：需求初稿，可进入产品与技术评审  
> 更新日期：2026-07-18  
> 产品定位：面向个人投资者的本地优先 A 股价值研究与多角色投资委员会桌面客户端

---

## 1. 文档摘要

Hanai Investment 将 A 股行情、自选股、价值估值与 AI 投资大师讨论整合在一个桌面客户端中。用户可以从全市场面板发现股票，查看实时行情和价值指标，再邀请巴菲特、芒格、段永平等“基于公开资料构建的 AI 模拟视角”独立分析或组成投资委员会。

产品依赖用户本机 Codex 提供 Agent 能力。行情、估值缓存、角色包、会话与运行文件默认存放在 ~/.hanai-investment；Agent 默认工作目录为 ~/.hanai-investment/runtime/workdir。

### 1.1 核心结论

1. 产品在技术上可行。Codex app-server 官方定位正是面向富客户端的深度集成接口，能够提供认证状态、会话历史、审批和流式 Agent 事件。
2. hanai-wealth 可参考其估值字段映射、估值曲线对齐和“结构化股票事实进入 Agent 上下文”的思路，但不应照搬每日静态 JSON 作为实时列表数据源。
3. nuwa-skill 是人物技能生成器，不是聊天 SDK 或群聊运行时。Hanai Investment 需要自行负责角色导入、版本、记忆、会话与群组编排。
4. GuruFocus/价值大师未公开接口只能用于技术验证，不能视为产品授权。现行条款限制将订阅数据用于面向终端用户的应用，并要求数据再分发取得商业许可。公开发布前，书面授权或商业数据许可是硬性门槛。
5. 产品必须定位为研究辅助工具，不接券商交易，不承诺收益，不把角色观点包装为真人意见或确定性投资建议。

## 2. 背景与问题

个人投资者通常需要在行情软件、财务网站、估值工具和 AI 对话产品之间反复切换，存在以下问题：

- 行情发现与价值判断割裂，实时价格和低频基本面经常被混为同一时效。
- 股票清单若依赖每日批量快照，无法满足盘中检索、自选股刷新和板块下钻。
- 通用 AI 容易给出缺少数据时间、来源和边界条件的“听起来合理”的结论。
- 单一角色容易形成锚定偏差；多个角色若没有共享证据与独立分析阶段，也只是多人设接龙。
- 用户希望复用本机 Codex 的账号、模型和 Agent 能力，而不是在新客户端中再次管理一套 API Key。
- 本地研究记录、角色资料和聊天历史需要可控、可备份、可删除。

Hanai Investment 的目标，是把“发现机会 → 查看事实 → 形成估值判断 → 多视角质询 → 留下可复核结论”做成一条连贯、本地优先的研究工作流。

## 3. 产品愿景与原则

### 3.1 产品愿景

让用户在五分钟内，从一只 A 股进入一份有事实来源、有角色分歧、有成立条件和失效条件的投资研究结论。

### 3.2 产品原则

1. **事实先于观点**：行情、财务、估值和角色判断必须分层展示。
2. **时间戳即产品能力**：所有外部数据都显示来源、数据时间、采集时间和缓存状态。
3. **分歧比假共识更有价值**：群组讨论不强行投票，不强行产生买入结论。
4. **本地优先，不等于本地推理**：文件默认留在本机；若 Codex 推理会把内容发送到外部服务，必须明确告知用户。
5. **可替换数据源**：任何未公开接口都不得成为不可替换的核心依赖。
6. **常驻的是身份与会话，不是无限后台运行**：角色可常驻侧栏，只有用户发起任务时才消耗 Agent 资源。
7. **不隐藏不确定性**：缺失、过期、冲突或推断的数据必须可见。

## 4. 产品范围与假设

### 4.1 默认产品假设

| 项目 | 默认定义 |
|---|---|
| 产品形态 | 桌面客户端 |
| 首发建议 | Windows 10/11 x64；架构保留 macOS、Linux 能力 |
| 默认语言 | 简体中文 |
| 市场范围 | MVP 覆盖沪深 A 股；北交所是否纳入需由数据许可和证券主数据确认 |
| 实时定义 | 近实时快照，不等同于交易所 L2 逐笔行情 |
| 主要用户 | 有自主决策能力的个人价值投资者 |
| 数据模式 | 本地证券主数据快速检索 + 可见数据按需刷新 + 估值低频缓存 |
| Agent 模式 | 用户本机 Codex app-server |
| 数据根目录 | ~/.hanai-investment |
| Agent 默认工作目录 | ~/.hanai-investment/runtime/workdir |

### 4.2 MVP 包含

- 首次启动、数据目录初始化和 Codex 环境检测。
- A 股今日 Dashboard。
- 指数、涨跌家数、涨停/跌停、成交额等市场概览。
- 行业或概念板块矩形树图热力图。
- 股票代码、名称和拼音检索。
- 自选股列表、分组和近实时行情刷新。
- 股票详情、基础指标、价值大师估值摘要与历史估值曲线。
- 角色中心、角色常驻侧栏和角色单聊。
- 一名主持人和至少一名参与角色的两轮书面讨论、逐轮归档及主持终审。
- 本地会话持久化、缓存管理、导出和数据清理。

### 4.3 MVP 不包含

- 券商账号、下单、自动交易或自动调仓。
- L2 逐笔行情和交易所级低延迟保证。
- 云同步和多人协作。
- 完整量化回测、组合优化和税务计算。
- 应用内执行 Nuwa 的完整人物蒸馏流程。
- 无人值守、无限轮次或长期后台自主 Agent。
- 确定收益、确定目标价或个性化买卖指令。
- 未经授权的数据再分发。

## 5. 目标用户与核心任务

### 5.1 目标用户

**价值研究型个人投资者**

- 关注企业质量、护城河、管理层、现金流和估值。
- 盘中希望快速掌握市场强弱，但不追求高频交易。
- 希望 AI 提供可质疑、可复核的研究框架，而非一句“可以买”。
- 重视本地数据控制，不希望把自选股和研究历史散落在多个产品中。

**角色与资料维护者**

- 使用 Nuwa 或其他合法来源生成人物技能。
- 需要导入、版本化、验证和更新角色。
- 需要知道每个角色的来源、许可证、研究截止日期和验证等级。

### 5.2 核心用户任务

1. 我想在盘中快速看到大盘、板块和市场宽度。
2. 我想输入代码、中文名或拼音立即找到股票并加入自选。
3. 我想区分“现在的价格”和“较慢更新的价值判断”。
4. 我想让一个指定角色从其投资框架分析当前股票。
5. 我想选择一名主持人与至少一名参与角色，让参与者先独立形成书面观点，再交叉复盘并由主持人给出终审结论。
6. 我想关闭应用后仍能恢复自选、角色和讨论历史。
7. 当 Codex 或数据源不可用时，我想知道问题在哪里，以及哪些功能仍然能用。

- Codex 状态。

## 7. 核心用户流程

### 7.1 首次启动

1. 应用检查并创建 ~/.hanai-investment 所需目录。
2. 显示隐私说明：文件默认本地保存；Codex 推理可能使用用户当前配置的外部模型服务。
3. 检查证券主数据和行情数据源。
4. 搜索本机 Codex 可执行文件并读取版本。
5. 启动 Codex app-server，完成协议初始化并读取账号状态。
6. 若 Codex 不可用，允许用户继续使用 Dashboard、搜索、自选和股票详情。
7. 用户进入今日市场页。

### 7.2 从市场发现到股票详情

1. 用户在板块树图查看涨跌分布。
2. 悬停查看板块涨跌、成交额、领涨股和数据时间。
3. 点击板块进入成分股视图。
4. 点击股票进入详情页。
5. 详情页分别显示实时行情、低频基本面、价值估值和缓存状态。

### 7.3 角色单聊

1. 用户在股票详情页点击“问一位大师”。
2. 选择角色。
3. 应用冻结当前股票证据包并展示包含的数据和时间。
4. 角色首次激活时声明其为基于公开资料的 AI 模拟视角。
5. 回复以流式方式展示，明确区分事实、框架推断和未知项。
6. 会话与角色版本、股票和证据快照绑定并持久化。

### 7.4 群组讨论

1. 用户选择一名主持人和至少一名参与角色。若只有一名参与者，主持人同时获得一个发言席，参加第一轮和第二轮。
2. 应用计算唯一 analysis-hash，并在 ~/.hanai-investment/runtime/workdir/<analysis-hash>/ 创建本次分析的固定目录。讨论开始后，所有相关 Agent 的 cwd 锁定为该目录，不得中途切换。
3. 应用生成唯一、不可变、带时间戳和内容哈希的股票证据包，并写入讨论清单。
4. 第一轮：应用先准备全部发言席的独立 Codex session，再以同一批次同时并发启动；不得逐个等待。各席位独立形成初始报告，且不得读取其他发言席的未封存观点。单参与者模式下，并发发言席为“主持人 + 唯一参与者”。
5. 第一轮全部完成或按失败策略收口后，应用校验报告、生成 manifests/turn01.json、计算文件哈希并封存，原文件不得覆盖修改。
6. 第二轮：应用为每个发言席构建包含其他所有已完成首轮报告的互评输入包；全部输入包准备完成后，再以新的同一批次同时并发启动全部发言席。各席位记录所读文件及哈希，并在新的第二轮文档中逐项回应、修正或坚持观点。
7. 若只有一名参与者，主持人与该参与者互读对方第一轮报告并分别生成 turn02.md；该模式仍构成两席交叉评审，不再使用“单人复盘”流程。
8. 第二轮全部完成或按失败策略收口后，应用生成 manifests/turn02.json 并封存。
9. 主持人只在第二轮封存后开始终审。主持人必须复用本次 analysis 中自己的既有 Codex thread/session，以新的 final-review turn 读取封存材料，并在主持人角色目录的 final.md 写入最终结论；不得为了终审另建 session。
10. 用户可中止讨论；已封存文档、哈希、阶段状态和已完成内容必须保留，可在重启后继续或结束。

## 8. 功能需求

优先级定义：

- P0：MVP 必须满足。
- P1：MVP 后首批增强。
- P2：后续规划。

### 8.1 应用基础与首次启动

| 编号 | 优先级 | 需求 |
|---|---|---|
| APP-001 | P0 | 首次启动时创建数据目录结构，重复启动不得覆盖已有数据。 |
| APP-002 | P0 | 应用启动不依赖 Codex 成功；Codex 故障只禁用 Agent 功能。 |
| APP-003 | P0 | 首页持续显示行情源、估值源和 Codex 三类健康状态。 |

| APP-007 | P1 | 支持自动更新检查；安装包和更新必须签名。 |

### 8.6 Dashboard 视觉与交互规格

视觉方向为“沉浸式研究终端”，而不是传统表格软件：

- 背景使用深石墨黑或深蓝黑；卡片采用低对比半透明层级。
- 强调色使用暖金或冷青，用于选择、焦点和 AI 状态，不与涨跌色争夺语义。
- A 股涨幅使用红色，跌幅使用绿色；同时用正负号、箭头、数值和纹理辅助，不能只靠颜色。
- 板块树图使用细边框、圆角和轻微内阴影；面积变化不得造成频繁跳动。
- 数据更新使用轻量闪烁或数字过渡，时长建议 150–240ms；尊重系统“减少动态效果”设置。
- 悬停卡片应在 100ms 内出现，避免遮挡当前板块。
- 窗口缩放时保持树图可读；小矩形只显示简称，完整信息放在提示层。
- 默认密度适合 1440×900；最低支持 1280×720，并兼容高 DPI。

### 8.12 讨论目录与文档归档

每次讨论在默认工作目录下使用独立、固定且可审计的分析目录。目录采用可读角色名加稳定 seat-id，避免重名和非法路径字符：

~~~text
runtime/workdir/<analysis-hash>/
├── analysis.json
├── evidence.json
├── codex-sessions.json
├── manifests/
│   ├── turn01.json
│   ├── turn02.json
│   └── final.json
├── <角色名>--<seat-id>/
│   ├── role.json
│   ├── turn01.md
│   ├── turn02.md
│   └── _attempts/
├── <主持人角色名>--moderator/
│   ├── role.json
│   ├── turn01.md
│   ├── turn02.md
│   ├── final.md
│   └── _attempts/
└── events.jsonl
~~~

只有一名参与者时的示例：

~~~text
runtime/workdir/7f3a...c912/
├── analysis.json
├── codex-sessions.json
├── 巴菲特--moderator/
│   ├── turn01.md
│   ├── turn02.md
│   └── final.md
└── 芒格--participant-01/
    ├── turn01.md
    └── turn02.md
~~~

归档规则：

- analysis-hash 是本次运行的唯一标识，由规范化股票 ID、evidence hash、主持人与参与席位及人物版本、议题、协议版本、创建时间和随机 nonce 计算 SHA-256；相同输入的不同运行不得复用旧目录。
- analysis.json 记录 analysis-hash、主题、股票、主持人、参与人、发言席、人物版本、证据哈希、预算、创建时间和当前阶段。
- 角色目录保留可读名称，但实际目录名为经过清洗的角色名加稳定 seat-id；不得直接使用未经校验的显示名作为路径。
- 只有一名参与者时，主持人目录包含 turn01.md、turn02.md 和 final.md；两名及以上参与者时，主持人默认只生成 final.md。
- 每个阶段只向参与者开放其专属输出路径；其他已封存报告只读。
- 角色可以形成报告内容，但最终归档由应用校验并原子写入，避免半份文档被误判为完成。
- 第二轮的互评输入包由应用从已封存文件构建，并记录输入包哈希；主持人的终审输入包也按同样方式构建。
- manifest 记录预期文件、实际文件、席位 ID、人物版本、Codex thread/session/turn ID、创建时间、字节数、SHA-256、状态和错误。
- 每轮 manifest 同时记录 roundBatchId、expectedSeats、应用侧批量调度时间、逐席位分发时间、Provider 实际开始时间和排队状态，用于证明本轮是否真正按并发批次启动。
- turn01 manifest 封存前，turn02 不得启动；turn02 manifest 封存前，主持人终审不得启动。
- 封存文件不可原地修改。需要更正时创建新修订或重新发起讨论，并保留原文件。
- 失败或重试的未封存输出写入角色目录的 _attempts/，成功后才生成规范文件 turn01.md、turn02.md 或 final.md。
- events.jsonl 记录阶段迁移、启动、中止、超时和归档事件，但不记录凭据。

### 8.13 两轮报告最低结构

每份 turn01.md、turn02.md 和 final.md 都必须包含可机器解析的 frontmatter，至少记录：

- analysisHash
- artifactType
- seatId
- personaId 与 personaVersion
- sessionOwnerKey
- codexThreadId
- codexSessionId
- codexTurnId
- purpose
- roundBatchId；final-review 可为空
- evidenceHash
- inputBundleHash
- createdAt
- status

第一轮发言席报告至少包含：

1. analysis-hash、seat-id、人物版本和 evidence hash。
2. 核心结论和置信度。
3. 引用证据 ID 的关键事实。
4. 商业模式、护城河、管理层、财务质量和估值判断。
5. 主要风险、未知项、成立条件和失效条件。
6. 希望其他参与者重点挑战的问题。

第二轮发言席报告至少包含：

1. 自己第一轮报告的路径和哈希。
2. reviewed-reports：所有应读其他发言席报告的路径、seat-id 和哈希。
3. 对每份同伴报告至少一个具体观点的回应。
4. 接受的观点、反对的观点及理由。
5. 相比第一轮新增、删除或修正的判断。
6. 更新后的条件式结论、置信度和仍未解决的问题。

若发言席数量大于一，而 reviewed-reports 缺少任一有效的其他发言席报告，turn02.md 不得通过校验。只有一名参与者时主持人也是发言席，因此双方必须互相阅读。

### 8.14 Codex 会话与分析文档映射

codex-sessions.json 和数据库必须建立 analysis、角色席位、Codex session、各轮 turn 与文档之间的双向关系。文件采用两级结构：顶层 `sessions[]` 每个角色只出现一次，每条 session 记录内部包含 `turns[]`。数据库对应拆分为 session 表与 turn/artifact 表，避免把同一角色的多个 turn 误建成多个 session。

Session 级字段：

| 字段 | 含义 |
|---|---|
| analysisHash | 本次分析目录及运行的唯一标识 |
| seatId | 本次分析中的席位标识，不等同于 personaId |
| seatRole | participant 或 moderator；主持人的发言和终审是同一席位的不同 turn purpose |
| personaId / personaVersion | 使用的人物定义及锁定版本 |
| sessionOwnerKey | analysisHash + seatId 的稳定组合键；本次分析内唯一 |
| codexThreadId | 该角色在本次分析中唯一的 app-server thread.id |
| codexSessionId | 该角色在本次分析中唯一的 thread.sessionId |
| sessionStatus | preparing、ready、running、session_unrecoverable 或 closed |
| createdAt / lastResumedAt | session 创建及最近一次成功恢复时间 |
| turns | 本角色按时间排序的 turn 映射数组 |

Turn 与文档级字段：

| 字段 | 含义 |
|---|---|
| codexTurnId | 本轮生成文档的 turn.id；同一 session 内唯一 |
| purpose | round01、round02、未来扩展轮次或 final-review |
| roundBatchId | 同一轮并发启动批次；该轮全部发言席共享此 ID；final-review 可为空 |
| inputBundleHash | 本轮实际输入包的哈希 |
| artifactPath / artifactSha256 | 相对 analysis 根目录的报告路径及封存哈希 |
| status | pending、running、completed、failed 或 interrupted |
| scheduledAt / dispatchedAt | 批次计划时间与客户端实际提交该角色 turn 的时间 |
| providerStartedAt / completedAt / queueState | Provider 实际开始、完成时间及内部排队状态 |
| supersedesTurnId | 同一 session 内重试时替代的旧 turn；不得用于替换 session |

单参与者模式的关系示例：

~~~json
{
  "analysisHash": "7f3a...c912",
  "sessions": [
    {
      "seatId": "moderator",
      "personaId": "buffett",
      "codexSessionId": "session-buffett-01",
      "turns": [
        { "purpose": "round01", "codexTurnId": "turn-b-01", "artifactPath": "巴菲特--moderator/turn01.md" },
        { "purpose": "round02", "codexTurnId": "turn-b-02", "artifactPath": "巴菲特--moderator/turn02.md" },
        { "purpose": "final-review", "codexTurnId": "turn-b-final", "artifactPath": "巴菲特--moderator/final.md" }
      ]
    },
    {
      "seatId": "participant-01",
      "personaId": "munger",
      "codexSessionId": "session-munger-01",
      "turns": [
        { "purpose": "round01", "codexTurnId": "turn-m-01", "artifactPath": "芒格--participant-01/turn01.md" },
        { "purpose": "round02", "codexTurnId": "turn-m-02", "artifactPath": "芒格--participant-01/turn02.md" }
      ]
    }
  ]
}
~~~

映射规则：

- 同一次 analysis 内，同一个角色席位必须使用一个固定 Codex thread/session 完成 turn01、turn02、未来扩展轮次，以及该席位承担的 final-review，并为每次输出分别记录 codexTurnId。
- `analysisHash + seatId` 在 codex-sessions.json 和数据库中施加唯一约束；同一 analysis 内不同 seatId 的 codexThreadId、codexSessionId 也必须互不相同。
- 角色人物版本在 analysis 创建时锁定；同一 personaId 不得在本次 analysis 中重复占据主持人与参与者等多个席位。
- analysis 创建阶段为全部预期角色并发创建各自唯一的 thread/session，且每个角色只创建一次；后续每轮只允许恢复或验证这批既有 session，禁止按轮次新建 session。只有整批 session 均达到 ready，或失败席位已按规则处理后，才能打开该轮启动门禁。
- 第一轮门禁打开时，所有发言席的首轮 turn 必须作为同一 roundBatchId 并发提交；第二轮所有互评输入包准备完成后，所有发言席的次轮 turn 也必须作为新的 roundBatchId 并发提交。实现中禁止在席位循环内逐个 await 完成结果。
- 只有一名参与者时，主持人的同一 session 连续承担第一轮发言、第二轮互评和最终总结；唯一参与者使用另一个独立 session 连续承担两轮。
- 主持终审作为主持人既有 session 中的新 final-review turn 执行；必须显式注入已封存证据、turn01、turn02 和 manifest，并在最终报告披露主持人是否同时参加前两轮。
- 每个 Markdown 文档的 frontmatter 与 codex-sessions.json 必须互相校验；任一 ID 或哈希不一致时，文档不得封存。
- 应用重启时必须按 codexThreadId 恢复 thread 并验证 sessionId；无法恢复时将席位标记为 session_unrecoverable，不得在相同 analysis 中创建新 thread/session 冒充延续。
- 同一个 Codex turn 只能对应一个规范归档文档；重试和中断产物进入 _attempts/。
- 数据库保存可查询索引，文件系统中的 analysis.json、codex-sessions.json 和 manifest 是可移植审计记录。

### 8.15 证据包

每次股票讨论生成一个 evidence snapshot，至少包含：

- 证券唯一标识、名称、交易所和行业分类。
- 行情快照、行情时间、数据源和延迟状态。
- 关键财务指标、财报期、币种、单位和数据源。
- 价值大师字段、估值标签、价值曲线摘要和数据日期。
- 用户主动添加的假设或材料，明确标为用户提供。
- 每个字段的证据 ID。
- 快照生成时间、内容哈希和 Schema 版本。

证据包要求：

- 生成后不可原地修改；刷新数据必须创建新版本。
- 角色可对同一事实得出不同解释，但不得自行改写证据值。
- Agent 默认不自行联网抓取新的价格或财务数字；如未来允许，必须作为新证据源进入审计链。
- 原始 HTML、网页指令或未清洗文本不得直接进入系统级提示，防止提示注入。

| 编号 | 优先级 | 需求 |

| SET-001 | P0 | 显示数据目录、Agent 工作目录和占用空间。 |
| SET-002 | P0 | 支持打开日志目录，但日志默认不记录完整聊天、凭据和股票私密备注。 |

## 9. 数据源与数据架构要求

### 9.1 数据源分层

| 数据类别 | 推荐策略 | 时效 | 失败策略 |
|---|---|---|---|
| 证券主数据 | 本地数据库，定期增量更新 | 日级或事件驱动 | 使用本地旧版本并标记更新时间 |
| 搜索 | 本地全文索引 | 即时 | 本地可用，不依赖实时网络 |
| 行情快照 | 东方财富类或正式授权行情 Provider | 盘中近实时 | 缓存 + 过期标记 |
| 指数与市场宽度 | 行情 Provider | 盘中近实时 | 局部降级，不阻断应用 |
| 板块与成分 | 行情 Provider | 分钟级或更低频 | 使用最近缓存 |
| 财务基本面 | 授权基本面 Provider | 财报期或日级 | 展示原始报告期 |
| 价值估值 | GuruFocus/价值大师或替代 Provider | 日级或按需 | 最近缓存或暂无估值 |
| Agent 观点 | 本机 Codex | 用户触发 | 可重试、可停止、保留已完成内容 |

### 9.2 Provider 边界

至少定义三类可替换能力：

- MarketDataProvider：证券主数据、搜索、行情、指数、市场宽度、板块和成分股。
- ValuationProvider：单股估值、财务指标、估值历史和供应商标签。
- AgentProvider：Codex app-server 连接、认证、模型、线程、轮次、流式事件和审批。

Provider 必须返回统一元数据：

- providerId
- sourceName
- sourceTimestamp
- fetchedAt
- freshness
- cacheState
- schemaVersion
- licenseMode
- errorCode

### 9.3 “实时”的产品定义

- 搜索响应实时：用户输入后立即从本地索引返回，不等待定时全量文件。
- 行情近实时：盘中按 Provider 能力对可见数据刷新；界面显示实际数据时间。
- 价值数据非实时：允许日级缓存，不与盘口时间混用。
- 界面不得使用“实时”掩盖延迟行情、缓存行情或日级基本面。

### 9.4 行情 Provider 约束

东方财富类网页接口可以作为个人原型适配器，但不能因为“公开可访问”就视为存在再分发许可。正式发布前必须完成：

1. 数据使用条款与再分发权确认。
2. 请求频率、用户规模与缓存策略确认。
3. 数据字段与时延口径确认。
4. 上游变更和停服替代方案确认。
5. 在产品中显示来源与适当声明。

AKShare 等封装库不能自动解决其底层数据源的授权问题。

## 11. Agent 与 Codex 集成设计约束

### 11.1 选择 app-server 的理由

OpenAI 官方将 Codex app-server 定义为嵌入自有产品的富客户端接口，可覆盖认证、会话历史、审批和流式事件。其协议基于双向 JSON-RPC，默认 stdio 传输为逐行 JSON；客户端需先 initialize/initialized，再创建 thread 和 turn，并持续接收事件。

MVP 因此采用：

- 单个受管理的 app-server 子进程。
- stdio/JSONL 作为默认传输。
- 每次 analysis 中，每个角色对应唯一且独立的 thread/session；该角色的所有轮次都在此 session 中以新 turn 延续。
- 群组讨论的主持人与各参与角色分别使用自己的独立 thread/session，共用一个 evidence snapshot，并将 cwd 固定为同一 analysis 根目录；不同角色的 session 不得复用或合并。
- 主持人兼任发言席时，第一轮、第二轮和终审都使用主持人的同一个 session；终审只是新的 final-review turn。
- turn/start 发起任务，流式事件更新 UI，turn/interrupt 负责取消。
- account/read 检测登录状态。
- model/list 动态获取模型能力。
- 所有 app-server 请求经统一适配层。

### 11.2 权限模型

- Agent 默认只访问 Hanai 的 runtime/workdir。
- 股票证据文件为只读输入；用户笔记的写入由应用控制。
- 第一轮期间，发言席只能访问证据与自己的输出；第二轮期间可只读访问全部已封存 turn01.md，并只能写自己目录的 turn02.md。
- 主持人终审期间只读访问证据与两轮归档，只能写自己角色目录的 final.md。
- 报告的最终落盘、结构校验和哈希封存由应用控制，Agent 不得覆盖其他角色或前序轮次文件。
- 默认禁止 Agent 任意访问用户其他目录。
- 默认禁止 Agent 自主执行交易、发送消息、修改系统配置或访问券商。
- 所有命令、文件修改、联网和扩权请求进入明确审批 UI。
- 不提供“永远允许所有操作”的一键默认选项。
- 主持人的 final-review turn 只做总结，不因进入终审阶段获得高于其他角色 Agent 的文件或网络权限。

### 11.3 兼容性

app-server 协议与部分能力仍可能随 Codex 版本变化，因此：

- 不通过单一版本字符串推断全部能力。
- 初始化后进行能力协商。
- 为 thread、turn、stream、account 和 approval 维护契约测试。
- 不兼容时显示已检测版本、支持范围和升级路径。
- WebSocket 在官方文档中仍为实验性且不受支持，MVP 不依赖它。

## 12. 角色与群组讨论设计

### 12.1 角色包模型

Nuwa 生成的人物包应被视为版本化研究资产，而不是直接执行的任意插件。角色至少包含：

- 身份与公开资料边界。
- 3–7 个心智模型。
- 5–10 个决策启发式。
- 表达风格与反模式。
- 时间线和观点变化。
- 诚实边界与不可回答范围。
- 资料来源和研究截止日期。
- 忠实度报告。

### 12.2 四类状态必须分离

1. 不可变、可版本化的人物定义。
2. 人物资料来源、许可证和研究截止时间。
3. 用户与该人物的持久聊天记忆。
4. 当前股票的共享证据快照。

角色升级不得静默改写历史消息；每条消息必须能够追溯当时的人物版本。

### 12.3 群组讨论状态机

主状态按以下顺序单向推进：

~~~text
created
  → evidence_locked
  → round1_running
  → round1_locked
  → round2_running
  → round2_locked
  → moderating
  → completed
~~~

任一运行阶段可以进入 cancelled、partial 或 failed，但已封存阶段不得回退或覆盖。

| 阶段 | 输入 | 输出 | 并发与门禁 |
|---|---|---|---|
| 创建分析 | 股票、主持人、参与人、预算 | analysis.json、analysis-hash 固定目录 | 单次 |
| 锁定证据 | 行情、财务、估值 | evidence.json 及哈希 | 后续只读 |
| 第一轮 | 相同证据、各自人物定义 | <角色目录>/turn01.md | 全部独立 session ready 后以同一 roundBatchId 并发 fan-out；席位间不得串行 await；相互隔离 |
| 封存第一轮 | 全部成功或已处理失败 | manifests/turn01.json | 第二轮启动门禁 |
| 第二轮互评 | 证据、自己的首轮、应用构建的全部其他席位首轮输入包 | <角色目录>/turn02.md | 全部输入包 ready 后以新的 roundBatchId 并发 fan-out；席位间不得串行 await；首轮只读 |
| 封存第二轮 | 全部成功或已处理失败 | manifests/turn02.json | 主持终审门禁 |
| 主持终审 | 应用构建的证据、两轮报告和清单输入包 | <主持人目录>/final.md | 在主持人本次 analysis 的既有 session 中启动新的 final-review turn |

阶段屏障处理：

- round1_running 或 round2_running 只能由整批启动操作进入：先确认本轮所有预期 session 与输入包均 ready，再一次性并发提交全部席位；不得先让部分席位运行，再等待其完成后启动剩余席位。
- 某参与者超时或失败时，不自动假设其同意其他观点。
- 应用提示用户选择“重试该角色、以缺席继续、结束为部分完成或取消讨论”。
- 以缺席继续时，manifest 记录缺席角色和原因；第二轮仅要求读取实际有效的第一轮报告。
- 主持人必须在最终报告首页声明讨论是否完整。

### 12.4 报告标准结构

主持人的 final.md 至少包含：

1. analysis-hash、股票、证据时间和 evidence hash。
2. 主持人身份、人物版本或中立主持版本。
3. 所有发言席、人物版本、席位角色和完成/缺席状态。
4. 主持人实际读取的第一轮和第二轮文档路径及哈希。
5. 已验证事实摘要，不新增证据包之外的数字事实。
6. 每个参与者第一轮到第二轮的观点变化。
7. 真正共识及其证据基础。
8. 未解决分歧及分歧来自事实、假设还是价值框架。
9. 主持人对关键争议的复盘与最终条件式结论。
10. 数据缺口和未知项。
11. 投资逻辑成立条件与失效条件。
12. 风险清单和建议的下一步研究动作。
13. 条件式状态：证据不足、暂不满足、等待条件、可进入进一步研究。
14. 讨论完整性声明和非投资建议声明。

## 13. 非功能需求

### 13.1 性能

| 编号 | 指标 |
|---|---|
| NFR-P01 | 冷启动到可交互目标 P95 小于 3 秒，不含首次下载证券主数据。 |
| NFR-P02 | 本地股票搜索 P95 小于 100ms。 |
| NFR-P03 | Dashboard 缓存首屏 P95 小于 1 秒；在线首批数据 P95 小于 2 秒。 |
| NFR-P04 | 行情收到后 1 秒内反映到可见 UI。 |
| NFR-P05 | 约 5,000 只股票的虚拟列表滚动无明显卡顿。 |
| NFR-P06 | 板块树图交互目标 60fps，最低可接受 45fps。 |
| NFR-P07 | Agent 发起后 3 秒内展示连接、排队或首段流式状态；不得长时间无反馈。 |

### 13.2 可靠性

- 单一 Provider 失败不得导致应用崩溃。
- 上游调用具备超时、有限重试、指数退避和抖动。
- Provider 连续失败后熔断，并显示下次重试时间。
- 数据库写入使用事务；迁移失败不得破坏原数据库。
- 应用崩溃后，已完成消息和报告可恢复。
- 所有缓存都能判断 Schema 版本，不读取不兼容缓存冒充新数据。

### 13.3 隐私

- 默认无云同步。
- 遥测默认关闭。
- 不采集自选股、聊天、证据包、持仓备注和凭据。
- 首次使用 Agent 前说明：本地 Codex 进程不代表模型推理一定在本地完成。
- 用户能够导出和删除自己的全部本地数据。

### 13.4 安全

- 前端页面不能访问任意本地文件或任意远端 URL。
- 使用严格内容安全策略。
- 数据 Provider 请求在受控后端适配层执行。
- 第三方人物包按不可信输入处理。
- 禁止自动执行导入包脚本。
- 防止路径穿越、符号链接逃逸和压缩包炸弹。
- 日志脱敏，禁止内置共享 API Key 或明文凭据。
- 安装包与更新签名。

### 13.5 可访问性

- 涨跌信息不能只用红绿颜色表达。
- 支持键盘导航和可见焦点。
- 关键文本与背景对比度达到 WCAG AA。
- 支持高 DPI 和系统字体缩放。
- 支持减少动态效果。
- 图表提供文本摘要或数据表替代视图。

### 13.6 可维护性

- Provider、Codex 协议和人物包解析分别拥有契约测试。
- 外部字段变更不得直接扩散到 UI。
- 所有数据迁移可回滚或保留备份。
- 关键错误有稳定错误码和用户可读说明。
- 发布说明记录数据源、Codex 兼容范围和人物包版本变化。

## 15. 验收标准

### 15.1 首次启动与 Codex

1. 在全新用户环境启动后，应用只在约定位置创建数据文件，并能再次启动。
2. 未安装 Codex 时，Dashboard、搜索、自选和详情仍可使用；Agent 入口显示安装说明。
3. 已安装未登录时显示“未登录”和可操作入口，不显示模糊的网络错误。
4. Codex 可用时完成 app-server 握手、账号读取和模型列表读取。
5. Windows 存在 codex.cmd 但 PowerShell 禁止脚本时，检测仍可成功。
6. Codex 崩溃后可重启，已完成消息不丢失。
7. 任意命令或扩权请求都能在 UI 中审查和拒绝。

### 15.2 搜索、自选与 Dashboard

1. 输入 600519、贵州茅台、拼音或首字母均能命中同一证券。
2. 搜索 P95 小于 100ms，断网时仍能搜索本地主数据。
3. 自选股重启后完整恢复，盘中可见行持续刷新。
4. 缓存行情不得显示为实时，必须显示数据时间和过期状态。
5. Dashboard 显示指数、市场宽度、成交额和板块树图。
6. 树图可以悬停查看详情，并可下钻到成分股。
7. 所有面板都能独立处理加载、空数据、过期和失败状态。
8. 红绿之外同时使用数值或符号表达涨跌。

### 15.3 股票详情与估值

1. 详情页明显区分实时行情、财务期数据、价值大师数据和 Agent 观点。
2. 每个外部数据区块显示来源、数据时间和采集时间。
3. 估值源成功时展示价值、偏离度、GF 分数、五维评分和历史曲线。
4. 估值源失败且有缓存时显示缓存和原始数据日期；无缓存时显示暂无估值。
5. 缺失值不得显示为零。
6. 供应商 Schema 异常时不会造成应用崩溃或错误投资标签。
7. 未授权的公开发行构建不会启用 GuruFocus 派生数据。

### 15.4 角色单聊

1. 每个角色显示来源、版本、许可证、研究截止日期和验证状态。
2. 缺少验证报告的角色显示“未验证”。
3. 首次回复出现一次模拟身份声明。
4. 具体股票回复引用证据时间和来源 ID。
5. 回复明确分为事实、角色推断和未知项。
6. “退出角色”立即退出角色模式。
7. 重启后会话仍绑定原角色版本与证据快照。
8. 导入包中的脚本不会自动执行。

### 15.5 群组讨论

1. 用户可选择一名主持人与至少一名参与者；主持人与参与人分别记录席位、身份和人物版本。
2. 每次讨论只使用一个 runtime/workdir/<analysis-hash>/ 固定目录，所有相关 Agent 的 cwd 一致且不中途改变。
3. 所有发言席接收相同 evidence snapshot 和哈希。
4. 第一轮开始前可看到与发言席数量一致且互不相同的 Codex session；所有首轮 turn 使用同一 roundBatchId 并发提交，正常本机条件下应用侧分发时间差不超过 1 秒，不能读取其他发言席未封存的 turn01.md。
5. 每个发言席在自己的角色目录生成 turn01.md；全部有效文档经校验、哈希和 manifest 封存后才能进入第二轮。
6. 第二轮全部互评输入包就绪后，所有发言席使用新的同一 roundBatchId 并发提交各自 turn；每个发言席生成新的 turn02.md，不覆盖第一轮，也不得等待上一席位完成后才启动下一席位。
7. 应用把全部有效的其他席位 turn01.md 全文和哈希送入每个第二轮 turn；每份 turn02.md 包含完整阅读回执，并至少具体回应每个其他席位的一个观点。
8. 只有一名参与者时，主持人自动成为第二个发言席：第一轮必须并行运行“主持人发言 session + 参与者 session”，第二轮也必须并行运行这两个 session；双方均生成 turn01.md、互读后均生成 turn02.md。
9. 第二轮 manifest 封存前，主持人不得开始终审。
10. 主持人复用本次 analysis 中自己唯一的既有 thread/session，以新的 final-review turn 读取 evidence、两轮全部有效报告和 manifest 后，在自己的角色目录生成 final.md，并列出所读文件及哈希。
11. 主持报告包含完整性、共识、分歧、观点变化、风险、未知、成立条件、失效条件和最终条件式结论。
12. 报告不宣布伪造的一致意见，不承诺收益，不触发交易。
13. 单个参与者失败时由用户选择重试、缺席继续、部分结束或取消；状态和原因写入 manifest。
14. analysis.json、codex-sessions.json、Markdown frontmatter 与数据库能互相追溯 analysis-hash、seat、persona、Codex thread/session/turn 和报告哈希。
15. 用户中止后不再发起新阶段；已封存输出可恢复，应用重启不会重复执行已完成轮次。
16. turn01/turn02 manifest 能通过 roundBatchId 和各席位时间戳证明批次调度；并发容量不足时整轮保持未启动并显示原因，不得在 UI 或归档中把串行补跑标记为并行。
17. 对任一角色检查 turn01.md、turn02.md 和其承担的 final.md，三者的 codexThreadId 与 codexSessionId 必须一致、codexTurnId 必须不同；任意两个不同角色的 codexSessionId 必须不同。
18. 同一角色 session 无法恢复时，系统不会在原 analysis 下生成替代 session；恢复失败状态、用户选择和后续处理均写入 events.jsonl 与 manifest。

### 15.6 数据管理

1. 所有核心用户数据位于 ~/.hanai-investment 或用户明确选择的新目录。
2. 凭据不以明文写入该目录或日志。
3. 清理缓存不会删除自选、人物或聊天。
4. 删除单次聊天后，数据库记录和对应运行文件均被移除。
5. 清除全部数据前必须二次确认，并可验证目标路径。
6. 仍安装的第三方内容保留其必需许可证通知。

## 20. 技术实现建议（非强制需求）

建议技术栈：

- Tauri 2：桌面壳、本地文件、SQLite、网络 Provider 和 Codex 子进程。
- Vue 3 + TypeScript：复用 hanai-wealth 的前端经验。
- Pinia：前端状态管理。
- ECharts：指数、K 线、雷达、树图和估值曲线。
- SQLite：证券主数据、自选、快照索引和会话元数据。

选择理由：

- 与参考项目 Vue/ECharts 经验接近。
- Rust 后端适合控制文件边界、Provider 请求和 Codex 子进程。
- 相比完整浏览器运行时，桌面包体和资源占用更可控。
- 可为 Windows、macOS 和 Linux 分别构建与签名。

该建议不改变本 PRD 的功能验收；若选 Electron 或其他桌面方案，仍需满足相同的数据、权限、性能和合规要求。

## 22. 最终定义

Hanai Investment 的 MVP 完成，不以“能显示行情并让几个角色聊天”为标准，而以以下结果为标准：

1. 用户可以快速发现和检索 A 股。
2. 实时行情、低频估值和 Agent 观点的时效与来源清晰分离。
3. 股票详情能展示可复核的价值证据，而不是一个黑盒分数。
4. 角色是有来源、有版本、有诚实边界的模拟研究视角。
5. 群组讨论能够保留分歧、条件和未知，而不是制造热闹或假共识。
6. Codex 缺失时产品仍可使用，Codex 可用时权限透明且可中止。
7. 用户数据默认留在 ~/.hanai-investment，Agent 默认运行在 ~/.hanai-investment/runtime/workdir。
8. 未取得数据和人物内容所需授权前，不将验证性原型包装为可公开发行产品。
